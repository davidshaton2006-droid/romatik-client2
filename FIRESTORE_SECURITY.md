# Firestore Security Rules

## Обзор

Правила безопасности настроены для защиты данных базы отдыха "Романтик" при одновременном разрешении клиентам создавать бронирования.

## Правила доступа по коллекциям

### 📝 Bookings (Бронирования)

**Кто может писать:**
- ✅ **Неавторизованные клиенты** — только CREATE новое бронирование
  - Требуется валидный формат данных
  - Требуется заполнить обязательные поля

**Кто может читать:**
- ✅ **Авторизованный персонал** (employee, marketing, management)

**Кто может обновлять:**
- ✅ **Персонал** (может обновлять статус, детали)

**Кто может удалять:**
- ✅ **Администратор** (management role)

### 📚 Booking History (Архив бронирований)

**Кто может читать/писать:**
- ✅ **Персонал** — чтение и архивирование

### 👤 Users (Профили персонала)

**Кто может читать:**
- ✅ Свой профиль (authenticated)
- ✅ **Администратор** — все профили

**Кто может писать:**
- ✅ **Администратор** — создание/обновление профилей

### 💰 Expenses (Расходы)

**Кто может читать/писать:**
- ✅ **Персонал** — управление расходами

**Кто может удалять:**
- ✅ **Администратор**

### 💵 Income (Доходы)

**Кто может читать/писать:**
- ✅ **Персонал** — ведение доходов

**Кто может удалять:**
- ✅ **Администратор**

### 📊 Analytics (Аналитика)

**Кто может читать:**
- ✅ **Персонал** — просмотр статистики

**Кто может писать:**
- ✅ **Администратор** — обновление метрик

### ⚙️ Settings (Настройки)

**Кто может читать/писать:**
- ✅ **Администратор** — управление настройками

## Валидация данных бронирования

При создании бронирования проверяются:

```
✓ Обязательные поля (house_type, check_in, check_out, guest_last_name, guest_phone, prepayment, created_at, created_by, created_by_name)
✓ Корректные типы данных
✓ Формат дат: YYYY-MM-DD
✓ Номер телефона: минимум 10 цифр
✓ Имя гостя: 2-100 символов
✓ Цены: положительные, не более 1,000,000 ₽
✓ Логика цен: prepayment ≤ total_price
```

## Роли пользователей

| Роль | Доступ |
|------|--------|
| **Неавторизованный** | CREATE bookings только |
| **employee** | READ/UPDATE bookings, expenses, income |
| **marketing** | READ bookings, READ analytics |
| **management** | READ/WRITE/DELETE все коллекции |

## Примеры использования

### Клиент создаёт бронирование (неавторизованный)
```javascript
// ✅ Разрешено
await setDoc(doc(db, 'bookings', bookingId), validBookingData);
```

### Персонал смотрит бронирования (авторизованный)
```javascript
// ✅ Разрешено
const query = query(collection(db, 'bookings'));
const snapshot = await getDocs(query);
```

### Клиент пытается читать бронирования
```javascript
// ❌ ЗАПРЕЩЕНО - нет авторизации
await getDocs(collection(db, 'bookings'));
```

### Персонал пытается удалить бронирование (не админ)
```javascript
// ❌ ЗАПРЕЩЕНО - нужна роль management
await deleteDoc(doc(db, 'bookings', bookingId));
```

## Развертывание правил

### Способ 1: Firebase Console
1. Перейти в Firebase Console
2. Firestore Database → Rules
3. Заменить содержимое на содержимое `firestore.rules`
4. Publish

### Способ 2: Firebase CLI
```bash
firebase deploy --only firestore:rules
```

## Тестирование правил

Firebase предоставляет встроенный эмулятор для локального тестирования:

```bash
firebase emulators:start
```

## Обновление правил (в будущем)

Если нужны изменения:
1. Отредактировать `firestore.rules`
2. Протестировать локально с эмулятором
3. Deploy в production

## Безопасность

### Что защищено:
✅ Данные персонала недоступны клиентам  
✅ Только персонал может читать расходы/доходы  
✅ Только неавторизованные могут создавать бронирования  
✅ Валидация на уровне БД (защита от некорректных данных)  
✅ Историческая отчетность только для персонала  

### Что разрешено:
✅ Клиенты создают бронирования  
✅ Персонал управляет бронированиями  
✅ Администраторы управляют всем  

## Примечания

- Правила работают только для веб/мобильных SDK
- Для backend операций использовать Admin SDK (с полным доступом)
- Периодически проверять логи безопасности в Firebase Console
